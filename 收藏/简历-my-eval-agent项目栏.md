## 一、简历版（可直接粘贴）

**my-eval-agent —— 评测工程师垂直 Agent（评估 Agent 的 Agent）** 
个人项目 | TypeScript / Node.js | github.com/shuangluo1206/my-eval-agent

从零手写的评测领域 Agent：给定一个待测 agent 的评测任务包，自动跑评测、
解析分数、复盘轨迹。三层架构（AI 层 / 循环层 / 工具层），零运行时依赖，
核心代码约 1500 行，6 个里程碑均有可复现验收。已接入真实数据分析 bench
任务包跑通全链路：一次对话自动完成「拉起被测 agent（9 轮 12 次工具调用）
→ 57 个判分点真判分（47.4/100）→ 读轨迹定位失分原因」，全程 2.2 分钟、
人工介入 0。

- 从零手写 Agent 主循环（不依赖 LangChain 等框架）：while 多轮循环 +
  流式工具调用参数碎片拼装 + 三出口控制流，统一事件流订阅模型
- AI 接入层：SSE 流式解析、OpenAI 兼容适配（同一 chunk 的 content 与
  tool_calls 双通道消费）、指数退避重试、Provider 注册表，支持任意
  OpenAI 方言网关即插即用
- 评测工具层：run_eval（子进程拉起评测脚本、AbortSignal 全链透传、
  产物 result.json 解析出分）+ read_trials（轨迹 jsonl 逐行摘要、
  tail 截尾防上下文爆炸）
- 垂直化三钩子：历史轨迹瘦身（整轮截断规避「孤儿 toolResult」引发的
  网关 422）、工具前置校验（拦截幻觉路径）、达标收尾（分数过阈值
  提前终止省 token）
- 多模型路由（主力 + 降级双模型）：主力开局失败当轮无缝切换（上层
  无感知）；基于模型质量缺陷的永久降级——降级触发条件来自 bench
  实测的模型脾气（write_file 丢 path）
- 工程化验收：fake provider 剧本回放做确定性测试（不烧 token）+
  真模型联调分层验收，5 个里程碑全部 PASS 后才进入下一个
- 真实 bench 接入：项目注册表 + 多级产物格式探测（outcome_grade /
  result.json）+ ducc 风格轨迹摘要适配，换同族 bench 项目零代码、
  一行注册即接入

## 三、30 秒电梯版（口头讲）

「市面上的 Agent 项目都是拿 Agent 做业务，我做的是拿 Agent 评 Agent——
我的日常工作就是给 agent 跑评测、复盘轨迹，所以我把这套流程做成了
自动化工具。整个项目从零手写，不用框架：AI 层对接 OpenAI 兼容网关、

降级条件用的就是我在 bench 里实测出来的模型毛病。最后接了真实 bench：
一句话下去，它自己拉起被测 agent、判分、翻轨迹、告诉我为什么丢分——
两分钟全程不用我管。每个里程碑都有确定性验收，不烧 token。」

## 四、面试深挖问答（预判 11 问）

### Q1：Agent 循环怎么转的？
一个 while(true)：把历史消息转成 LLM 消息 → 调模型流式收事件、
边收边拼 → assistant 消息入历史 → 没有工具调用就收工（出口①）；
有就执行工具、结果入历史 → 所有工具说 terminate 就收工（出口②）；
否则带着工具结果回循环顶再问模型。入口还有 isStreaming 检查防并发。
（对照 src/agent/loop.ts 的 runLoop）

### Q2：工具调用的参数是怎么来的？
模型吐的是流式碎片：tool_call_start 开罐、tool_call_delta 一片片
到、done 时整体 JSON.parse。碎片单独哪个都不是合法 JSON，必须在
done 时攒一起 parse；parse 失败还要兜底把原始字符串塞回去，保证
循环转得下去。（loop.ts processLLMStream，my-easy-pi 同款坑）

### Q3：工具执行失败怎么办？
三层兜底：工具不存在→回 isError 的 toolResult 让模型换姿势；
工具抛异常→catch 住转 isError 结果，循环不炸；前置校验钩子直接
拦截非法调用并给出理由。原则是「失败是模型能看到的信息，不是崩溃」。

### Q4：为什么要手写，不用 LangChain？
三个理由：①求职目标是搞懂原理，框架把循环藏起来了；②垂直场景
要对循环做精确控制（三钩子插队口），框架的抽象反而挡路；③零运行时
依赖、1500 行核心，面试每一行都能讲。框架该学还是学，但手写一遍
之后再学，看什么都是透明的。

### Q5：上下文爆了怎么办？
transformContext 钩子做轨迹瘦身：历史超过阈值就整轮砍掉旧消息换成
摘要（含工具调用数、错误数的统计）。关键细节：截断点必须落在
「非 toolResult 边界」，否则 assistant(带 toolCalls) 被砍、toolResult
留下来变孤儿，OpenAI 方言网关直接 422——这是实测踩出来的。

### Q6：多模型路由的策略是怎么设计的？
分两类失败：网络/网关错误（开局一个字没吐）→ 当轮无缝切备用，
错误事件不外传，上层无感知，但不算降级，可能是偶发抖动；质量缺陷
（write_file 丢 path，bench 实测的模型脾气）→ 连败计数触发永久
降级。区分「环境问题」和「模型问题」是策略核心。（src/ai/router.ts）

### Q7：怎么测试的？烧不烧 token？
双轨：fake provider 按剧本回放事件流做确定性验收（碎片拼装、钩子
触发、路由切换都有断言，不烧 token 不碰网络）；真模型联调放在
里程碑验收（m3 烧少量 token 验证全链路）。改动后回归跑 M2/M4/M5。

### Q8：评测「垂直」体现在哪？跟通用 Agent 差在哪？
循环一行评测逻辑都不懂，垂直智能全在外面插：工具层是 run_eval/
read_trials 这种评测专用工具；三钩子的规则全是评测经验（轨迹要留
档复盘所以瘦身不删盘上文件、分数达标就收工省 token、幻觉路径
必须拦不然模型连环重试）。真实跑过的例子：被测 agent 9 轮操作全成功
却只拿 47.4 分，eval-agent 复盘结论是「失分不在执行层、在分析结果的
正确性」——这种解读正是评测工程师的日常，也是垂直工具喂给模型的结构
化轨迹摘要才做得到的。通用循环+垂直插件，换领域只换插件。

### Q9：下一步会做什么？
对照模式：同一任务双模型跑分对比（评测工程师的 A/B 试）；轨迹智能
分析（从「摘要」到「归因」——现在能读出「操作全成功但分数低」，下一步
是自动把 47.4 分拆解到 21 个失败判分点上，指出每个失败对应轨迹哪一步）。
（真实 bench 接入已完成：一次对话跑通拉起 agent→判分→复盘全链路。）

### Q10：你这个 Agent 能做数学题吗？比如 1+1？
能答，但答对的功劳不属于 Agent 架构——那是底层模型的通用能力从垂直
Agent 的壳里漏出来的。实测过（探针实验，2026-10-01）：给它装上全部
评测工具（run_eval / read_trials）问「1+1=」，一次工具都没调、纯文字
回答「1+1=2」——题目落不进任何工具的参数面，模型直接用世界知识答了。
这恰好证明了垂直化的边界：**工具箱定义了 Agent 的能力面，模型只负责
在能力面内做决策**；题目落在能力面外时，它退化为一个普通 chatbot。
而真要「正经」用评测流水线做，得把 1+1 造成 bench 任务（instruction
+ 判分器 + 注册）再跑——能做，但评测流水线的成本只在题目复杂到需要
多步执行时才值得付。这个回答同时展示了「分得清模型的功劳和架构的
功劳」——评测工程师的核心素养。

智能永远来自模型（GLM）；你的 eval 决定这份智能能不能用得上、用得对不对。 题目落在工具能力面内 → 架构放大模型的能力（1+1 → 工位闲置）；落在能力面外 → 模型退化为裸 chatbot。

### Q11：所以你这个项目的交付物到底是什么？
是架构，模型是插上去的零件。GLM 只是配置里一行可替换的字符串，
真正「我写的」是三层架构 + 垂直化工程决策：AI 层（SSE 拆包、Provider、
路由）、循环层（while 主循环）、工具层（run_eval / read_trials）、
三钩子、格式家族适配器。两个证据：①换模型零改码——GLM-5.3 换
DeepSeek-V4-Pro 架构一行不动（M5 路由器连自动切换都演示过）；
②探针实验反向证明——把模型抽走，架构连「答题」这个动作都不存在。
标准表述：「模型不是我做的，评测也不是我出的——我做的是中间那层：
让任意模型接上任意 bench 的执行架构。三钩子和路由器解决的都是模型
不可靠的问题：模型会忘（所以要瘦身）、会编（所以要拦截）、会菜
（所以要降级）。架构存在的意义，就是把这些不可靠兜住。」

  是评测工程师和「调了个 API 的人」的区别
